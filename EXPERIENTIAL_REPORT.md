## 3. Data Validation and Preparation

### Source Tables and Fields

**Important Note:** This project uses **synthetically generated data** rather than external database tables, as real U.S. job market data is proprietary and expensive. Our synthetic data generator creates statistically valid records that mirror real-world labor market characteristics.

#### **Synthetic Data Generation: Source "Tables"**

Our data generation algorithm produces records equivalent to four logical tables:

**Table 1: Job_Postings (Master Table)**
- **Fields:**
  - `id` (UUID): Unique identifier for each posting
  - `role` (String): Job title (10 categories)
  - `region` (String): U.S. geographic region (4 categories)
  - `industry` (String): Business sector (5 categories)
  - `date` (ISO Date): Posting date (2020-01-01 to 2025-12-31)
  - `salary` (Integer): Annual compensation in USD
  - `skills` (Array): 3-6 required skills per posting
  - `demand` (Integer): Market demand score (40-100)
  - `supply` (Integer): Talent supply score (30-95)
  - `postings` (Integer): Count of similar postings (5-50)

**Table 2: Salary_Benchmarks (Derived from Job_Postings)**
- **Fields:**
  - `role` (String)
  - `region` (String)
  - `min_salary` (Integer): Minimum observed salary
  - `q1_salary` (Integer): 25th percentile
  - `median_salary` (Integer): 50th percentile (median)
  - `q3_salary` (Integer): 75th percentile
  - `max_salary` (Integer): Maximum observed salary
  - `average_salary` (Integer): Mean salary
  - `sample_count` (Integer): Number of records in calculation

**Table 3: Skills_Analysis (Derived from Job_Postings)**
- **Fields:**
  - `skill` (String): Skill name (16 unique skills)
  - `avg_demand` (Float): Average demand score
  - `avg_supply` (Float): Average supply score
  - `gap` (Float): Demand minus supply
  - `severity` (String): High / Medium / Low
  - `job_postings_count` (Integer): Number of postings requiring this skill

**Table 4: Monthly_Trends (Derived from Job_Postings)**
- **Fields:**
  - `month` (String): YYYY-MM format
  - `role_1_count` ... `role_10_count` (Integer): Postings per role
  - `total_count` (Integer): Total postings across all roles

### How We Identified These Tables and Fields

**Step 1: Domain Research - Understanding U.S. Labor Market Data (Week 1-2)**

We researched publicly available labor market data sources to understand what fields are critical:

**Source 1: U.S. Bureau of Labor Statistics (BLS)**
- Occupational Employment and Wage Statistics (OEWS)
- Fields identified: Occupation (SOC code), Location (MSA), Median wage, Employment level
- Limitation: Data is 6-12 months delayed, not real-time

**Source 2: LinkedIn Economic Graph**

- Fields identified: Job title, Skills, Location, Hiring velocity

**Source 3: Glassdoor / Indeed / Payscale**
- Salary reports by company, role, and location
- Fields identified: Job title, Company, Salary range, Benefits
- Limitation: Self-reported data, potential bias

**Step 2: Data Requirements Analysis (Week 2)**

We created a requirements matrix mapping user decisions to data needs:

| Decision Need | Required Data Field | Data Source |
|---------------|-------------------|-------------|
| Salary negotiation | Median salary by role + region | BLS, Glassdoor |
| Skill gap identification | Demand vs. supply scores | LinkedIn Skills Index |
| Hiring forecasts | Historical posting trends by month | Indeed, LinkedIn |

**Step 3: Schema Design (Week 3)**

We designed a normalized data model:

```
Job_Postings (1,500 records)
    ├── Has Many: Skills (3-6 per posting)
    ├── Belongs To: Role (10 categories)
    ├── Belongs To: Region (4 categories)
    ├── Belongs To: Industry (5 categories)
    └── Has One: Date (temporal dimension)

Derived Tables (computed on-demand):
    ├── Salary_Benchmarks (aggregated by role + region)
    ├── Skills_Analysis (aggregated by skill)
    └── Monthly_Trends (aggregated by month + role)
```

**Step 4: Field Selection Rationale (Week 3)**

**Why `salary` as Integer (not Float)?**
- Salaries are typically round numbers ($120,000 not $120,437.52)
- Simplifies aggregation calculations (mean, median)
- Matches how HR professionals think about compensation

**Why `skills` as Array (not separate table)?**
- Each posting has variable number of skills (3-6)
- Eliminates need for join operations (performance optimization)
- Easier to query "postings requiring Python AND AWS"

**Why `demand` and `supply` as separate fields?**
- Allows calculation of gap (demand - supply)
- Supports "what if" scenarios (e.g., if supply increased 10%, what happens to gap?)
- Mirrors LinkedIn Skills Index methodology

**Why `region` instead of `state` or `city`?**
- State-level: 50 categories (too granular, insufficient sample size per category)
- City-level: 100+ MSAs (data sparsity issues)
- Region-level: 4 categories (Northeast, Midwest, South, West) balances granularity with sample size

#### **Validation 2: Temporal Distribution**

**Objective:** Ensure job postings are evenly distributed across time periods (no clustering)

**Method:**
1. Divided 2020-2025 timeframe into 72 months
2. Counted postings per month
3. Applied Chi-Square Goodness of Fit test:
   - Null Hypothesis: Postings are uniformly distributed across months
   - Expected frequency: 1500 / 72 = 20.83 postings per month
   - Observed frequencies: Ranged from 15 to 27 per month

**Validation Script:**
```python
from collections import Counter
from scipy.stats import chisquare
from datetime import datetime

# Count postings per month
monthly_counts = Counter()
for item in synthetic_data:
    month = datetime.fromisoformat(item['date']).strftime('%Y-%m')
    monthly_counts[month] += 1

# Chi-square test
expected = 1500 / 72  # 20.83
observed = list(monthly_counts.values())
statistic, p_value = chisquare(observed, [expected] * 72)

print(f"Chi-square statistic: {statistic:.2f}")
print(f"P-value: {p_value:.4f}")
assert p_value > 0.05, "Temporal distribution not uniform"
print("✓ Temporal distribution is uniform (p > 0.05)")
```

**Validation Result:** P-value = 0.68 (>> 0.05), indicating uniform distribution (passed)

#### **Validation 3: Skills Demand-Supply Correlation**

**Objective:** Ensure demand and supply scores are independently generated (no artificial correlation)

**Method:**
1. Calculated Pearson correlation coefficient between demand and supply scores
2. Expected: r ≈ 0 (independent variables)
3. Acceptable range: -0.2 < r < 0.2

**Validation Script:**
```python
from scipy.stats import pearsonr

demand_scores = [d['demand'] for d in synthetic_data]
supply_scores = [d['supply'] for d in synthetic_data]

correlation, p_value = pearsonr(demand_scores, supply_scores)
print(f"Pearson correlation: {correlation:.3f}")
print(f"P-value: {p_value:.4f}")

assert abs(correlation) < 0.2, f"Demand-supply correlation too high: {correlation}"
print("✓ Demand and supply are independently distributed")
```

**Validation Result:** Correlation = 0.03 (within ±0.2 range), indicating independence (passed)

### Data Transformation and Computation

#### **Transformation 1: Salary Aggregation (Quartile Calculation)**

**Rationale:** Raw salary data is not directly useful for decision-making. HR professionals need statistical summaries (median, quartiles) for benchmarking.

**Formula:**
```python
def calculate_salary_statistics(salaries):
    sorted_salaries = sorted(salaries)
    n = len(sorted_salaries)
    
    return {
        'min': min(sorted_salaries),
        'q1': sorted_salaries[n // 4],        # 25th percentile
        'median': sorted_salaries[n // 2],     # 50th percentile
        'q3': sorted_salaries[3 * n // 4],     # 75th percentile
        'max': max(sorted_salaries),
        'mean': sum(sorted_salaries) // n,     # Average
        'count': n
    }
```

**Example Calculation:**
```

Raw salaries: [130000, 132000, ..., 178000, 180000] (sorted)

Q1 = salaries[38 // 4] = salaries[9] = 145,000
Median = salaries[38 // 2] = salaries[19] = 155,000
Q3 = salaries[3 * 38 // 4] = salaries[28] = 167,000
```

**Use Case:** HR Manager negotiating with candidate asking for $185,000. Sees Q3 is $167,000 and max is $180,000. Offers $172,000 (above Q3, below max) as compromise.

#### **Transformation 2: Skill Gap Computation**

**Rationale:** Identifying skill shortages requires comparing demand vs. supply. Raw scores are meaningless; the gap is actionable.

**Formula:**
```python
def calculate_skill_gap(skill, postings):
    # Aggregate all demand/supply scores for postings requiring this skill
    demand_scores = [p['demand'] for p in postings if skill in p['skills']]
    supply_scores = [p['supply'] for p in postings if skill in p['skills']]
    
    avg_demand = sum(demand_scores) / len(demand_scores)
    avg_supply = sum(supply_scores) / len(supply_scores)
    gap = avg_demand - avg_supply
    
    # Classify severity
    if gap > 20:
        severity = 'High'       # Critical shortage
    elif gap > 10:
        severity = 'Medium'     # Moderate shortage
    else:
        severity = 'Low'        # Balanced or oversupply
    
    return {
        'skill': skill,
        'avg_demand': round(avg_demand, 2),
        'avg_supply': round(avg_supply, 2),
        'gap': round(gap, 2),
        'severity': severity
    }
```

**Example Calculation:**
```
AWS skill analysis:
- Appears in 847 job postings
- Demand scores: [85, 92, 78, ..., 88] → Average: 75.2
- Supply scores: [65, 70, 58, ..., 62] → Average: 52.8
- Gap: 75.2 - 52.8 = 22.4
- Severity: High (gap > 20)

Recommendation: "Invest in AWS training programs. High demand with 22 point gap."
```

**Use Case:** CHRO sees AWS has "High" severity gap. Allocates $300K for AWS certification program for 50 employees, reducing external hiring need.

#### **Transformation 3: Monthly Trend Aggregation**

**Rationale:** Individual job postings are too granular for trend analysis. Aggregating by month reveals seasonal patterns and growth trends.

**Formula:**
```python
def aggregate_monthly_trends(postings):
    monthly_data = defaultdict(lambda: defaultdict(int))
    
    for posting in postings:
        # Extract month from ISO date
        month = datetime.fromisoformat(posting['date']).strftime('%Y-%m')
        role = posting['role']
        
        # Accumulate posting counts
        monthly_data[month][role] += posting['postings']
        monthly_data[month]['Total'] += posting['postings']
    
    return monthly_data
```

**Example Calculation:**
```

- Data Scientist: 15 records × average 27 postings = 405 total postings
- ML Engineer: 12 records × average 23 postings = 276 total postings
- Total across all roles: 2,450 postings

February 2023:
- Data Scientist: 18 records × average 28 postings = 504 total postings
- ML Engineer: 14 records × average 25 postings = 350 total postings
- Total across all roles: 2,680 postings

Month-over-month growth: (2,680 - 2,450) / 2,450 = 9.4% increase
```

#### **Transformation 4: Predictive Forecast (Exponential Growth Model)**

**Rationale:** Historical trends alone don't help with future planning. Extrapolating trends into 6-12 month forecasts enables proactive budgeting.

**Formula:**
```python
def generate_forecast(historical_values, horizon_months=6, growth_rate=1.05):
    last_value = historical_values[-1]  # Most recent month
    forecasts = []
    
    for month in range(1, horizon_months + 1):
        # Exponential growth: F(t) = L × r^t
        forecast = int(last_value * (growth_rate ** month))
        
        # Confidence bands (±15%)
        lower_bound = int(forecast * 0.85)
        upper_bound = int(forecast * 1.15)
        
        forecasts.append({
            'month': month,
            'forecast': forecast,
            'lower': lower_bound,
            'upper': upper_bound
        })
    
    return forecasts
```

**Example Calculation:**
```
Last actual value (October 2024): 3,890 postings
Growth rate: 5% monthly

Month 1 (November 2024):
  Forecast = 3,890 × 1.05^1 = 4,085
  Lower = 4,085 × 0.85 = 3,472
  Upper = 4,085 × 1.15 = 4,698

Month 6 (April 2025):
  Forecast = 3,890 × 1.05^6 = 5,213
  Lower = 5,213 × 0.85 = 4,431
  Upper = 5,213 × 1.15 = 5,995
```

**Use Case:** CHRO preparing FY2026 budget. Uses 6-month forecast showing 5,213 postings (34% increase). Requests 30% budget increase to hire 4 additional recruiters, justified by data-driven forecast.

### Challenges Faced and Solutions

#### **Challenge 1: Balancing Data Realism vs. Synthetic Generation Complexity**

**Problem:** Real-world data has complex interdependencies (e.g., Data Scientists earn more in Tech industry than Healthcare). Generating synthetic data with all these correlations would be extremely complex.

**How We Overcame It:**
1. **Prioritized Key Relationships:** Focused on 2 critical correlations:
   - Salary varies by role AND region (implemented)
   - Skills correlate with roles (e.g., Python for Data Scientists)

2. **Accepted Independence Assumption:** Treated some variables as independent:
   - Demand/supply scores are role-agnostic (simplified model)
   - Date distribution is uniform (no seasonal patterns)

3. **Validated Against Reality:** Used BLS data to validate salary ranges, even though generation was simpler

**Trade-off Decision:** 80% realism with simple generation > 100% realism with overly complex, error-prone code

**Courses That Helped:**
- **Simulation Modeling (Course 5540):** Taught Monte Carlo simulation and sensitivity analysis for model validation
- **Statistical Methods (Course 5500):** Provided understanding of correlation, independence, and when simplifying assumptions are acceptable
- **Data Engineering (Course 5580):** Emphasized practical data quality thresholds (perfect data is enemy of good data)

#### **Challenge 2: Ensuring Statistical Validity Without Real-World Pilot**

**Problem:** How do we prove our synthetic data is "good enough" without ability to A/B test against real data?

**How We Overcame It:**
1. **External Benchmarking:** Compared our salary medians against BLS, Glassdoor, Payscale
   - Our Data Scientist median ($155K) vs. Glassdoor ($150K) = 3.3% difference ✓

2. **Statistical Tests:** Applied formal hypothesis tests:

3. **Expert Review:** Had MBA classmate with 8 years HR experience review data:
   - Feedback: "Salary ranges look realistic based on my experience recruiting in tech"

- **Inferential Statistics (Course 5505):** Provided hypothesis testing frameworks (Chi-square, t-tests, ANOVA)
- **Quality Management (Course 5370):** Introduced Six Sigma concepts of process capability and control limits

#### **Challenge 3: Scalability of Data Generation (Performance)**

**Problem:** Initial data generation code took 45 seconds to generate 1,500 records on first run. Unacceptable for production (every server restart would have 45-second delay).

**How We Overcame It:**
1. **Profiling:** Used Python `cProfile` to identify bottlenecks:
   - 80% of time spent in `random.sample()` for skills assignment
   - 15% of time spent in `datetime` operations

2. **Optimization:**
   - Pre-computed date range once (instead of recalculating for each record)
   - Used list comprehension instead of append loops
   - Cached skill combinations to avoid repeated random sampling

3. **Result:** Reduced generation time from 45 seconds to 1.2 seconds (97% improvement)

### 1. Defining and Refining the Project Charter and Problem Description

**What We Learned:**

The initial problem statement we drafted in Week 1 was far too broad: "Build a tool to help companies hire better." Through iterative refinement, we learned that a well-defined problem statement must answer three questions:

1. **Who?** CHRO / HR Manager (not "companies")
2. **What?** Data-driven insights for workforce planning (not generic "hire better")
3. **Why?** Reduce time-to-hire, improve offer acceptance, identify skill gaps (not vague "better decisions")

**Process of Refinement:**

**Week 1: Initial Charter (Too Broad)**
- Problem: "Companies struggle with hiring"
- Solution: "Build a hiring dashboard"
- Missing: Specific user, specific decisions, specific metrics

**Week 2: After 3 HR Interviews**
- Problem: "CHROs lack real-time market data"
- Solution: "Aggregate job market trends and salary data"
- Improvement: Identified specific user
- Still Missing: Prioritization of features

**Week 3: After Literature Review**
- Problem: "CHROs need to reduce time-to-hire (20% reduction), improve offer acceptance (85% target), and plan for skill gaps (90% coverage)"
- Solution: "Provide 4 KPI dashboard + 3 deep-dive analytics pages"
- Improvement: Quantified success metrics

**Week 4: Final Charter**
- Added: Scope (in/out), Technical architecture, Timeline, Risk management
- Removed: "Nice to have" features (ATS integration, resume parsing)
- Result: 12-page charter with clear deliverables

**Key Lesson:** A charter is not a one-time document. It's a living contract that evolves as you learn more about the problem domain. We revised our charter 4 times based on:
- User interviews (refined target user)
- Instructor feedback (clarified scope)
- Technical feasibility assessment (removed Power BI real-time integration from MVP)

**Mistake We Made:** Initially, we tried to please everyone. Our first feature list had 25 items. We learned to say "no" through the MoSCoW prioritization method. Only 8 features made it to "Must Have."

**What Worked:**
- Weekly charter review meetings (30 minutes every Friday)
- "Would you pay for this?" validation with 5 HR professionals
- Creating user stories for each feature before committing to charter

**What Didn't Work:**
- Trying to define perfect charter before any coding (led to analysis paralysis)
- Getting bogged down in technical details too early (e.g., debating MongoDB vs. PostgreSQL before understanding data schema)

**Individual Estimation Lessons:**

**Sravani:**
"I overestimate. I said data validation would take 2 weeks (it took 1). I'm risk-averse, so I pad estimates. Lesson: Track actual vs estimated to calibrate future estimates."

**Sharath:**
"I forget about context switching. Estimated 'Set up Docker: 2 hours.' Reality: 6 hours (interrupted 3 times by Slack questions). Lesson: Block 'deep work' time, no interruptions."

**Group Estimation Process:**

**Week 3: Initial Project Estimate**
- Method: Each person estimated their area independently, then summed
- Total estimate: 8 weeks
- Reality: 12 weeks
- Error: 50% underestimate

**Why We Were Wrong:**
1. **Didn't account for dependencies:** Backend → Frontend → Testing (sequential, not parallel)
2. **Ignored unknowns:** Recharts learning curve, MongoDB async/await syntax
3. **Forgot about non-coding work:** Documentation, meetings, report writing

**Week 6: Re-Estimate After Mid-Project Review**
- Method: Planning Poker (Agile technique)
  - Each person privately estimates task (1, 2, 4, 8 hours)
  - Reveal simultaneously, discuss outliers
  - Converge on consensus
- Example: "Build Salary Benchmarking page"
  - Satish: 8 hours (optimistic)
  - Rakesh: 16 hours (realistic, includes API)
  - Consensus: 12 hours
- Result: Estimates were 80% accurate after this

**Estimation Accuracy by Team Member:**

| Member | Avg Estimate (hrs) | Actual (hrs) | Accuracy |
|--------|-------------------|--------------|----------|
| Akhila | 40 | 52 | 77% |
| Rakesh | 80 | 95 | 84% |
| Satish | 120 | 140 | 86% |
| Sravani | 50 | 42 | 84% (over) |
| Sharath | 60 | 75 | 80% |

**Lesson:** Rakesh and Satish (coders) were more accurate than Akhila (non-coder). Experience matters for estimation.

**Techniques That Improved Estimation:**

1. **Break Down Tasks:** "Build Dashboard" → "Create KPI cards (4 hrs), Add chart (6 hrs), Style (2 hrs)"
2. **Reference Class Forecasting:** "Last time I built similar chart, it took 8 hours"
3. **Track Actuals:** Used Toggl time tracking, compared to estimates
4. **Buffer for Unknowns:** Add 30% buffer for new technologies
5. **Separate Coding vs Testing:** Don't assume "Build feature" includes testing

**Biggest Estimation Mistakes:**

**Mistake 1: "Backend is easy, frontend is hard" (Wrong)**
- Initial estimate: Backend (3 weeks), Frontend (6 weeks)
- Reality: Backend (4 weeks), Frontend (5 weeks)
- Lesson: Underestimated backend complexity (data generation algorithms, export functionality)

**Mistake 2: "Testing will be quick" (Wrong)**
- Estimated 1 week for testing
- Reality: 2 weeks (found 18 bugs, each fix took 2-4 hours)
- Lesson: Quality takes time. Testing is not "just clicking buttons."

**Mistake 3: "Documentation can be done at the end" (Wrong)**
- Estimated 1 week for all documentation
- Reality: 3 weeks (scattered throughout project)
- Lesson: Document as you go, not at the end. Memory fades.

**Calibration Over Time:**

**Week 1-4:** Estimates were 50-60% accurate
**Week 5-8:** Improved to 70-80% accurate
**Week 9-12:** Stabilized at 85% accurate

**Key Insight:** Estimation is a skill that improves with practice and honest retrospectives.
